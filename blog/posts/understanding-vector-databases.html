Understanding Vector Databases

What embeddings are, why similarity search needs its own kind of index, and when a plain Postgres table is all you need.

09 Sep 2026·2 min read·Tech / AI
On this page

Every time a tool says it does "semantic search", there is a vector database somewhere underneath. The idea is simpler than the marketing: turn things into lists of numbers, then find the lists that sit closest together.

01What an embedding is

An embedding model reads a piece of text, an image or a sensor trace and returns a fixed-length vector, often a few hundred to a few thousand numbers. Things that mean similar things land near each other, so "chole bhature" ends up closer to "breakfast in Old Delhi" than to "turbopump seal".

The vectors only mean something relative to each other, and only for the model that made them. Mixing vectors from two different models in one index gives you nonsense distances.

02Why it needs its own index

A normal database index answers "which rows equal this value?" Similarity search asks "which rows are nearest to this point?" in hundreds of dimensions, and B-trees don't help with that.

  • ExactCompare the query with every stored vector. Always correct, and slower as the table grows.
  • HNSWA layered graph you walk towards the query. Fast and accurate, and it uses more memory.
  • IVFSplit vectors into clusters and only search the closest few. Smaller, with a recall trade-off you tune.

The last two are approximate: they can miss a true neighbour now and then, in exchange for answering in milliseconds instead of seconds.

03A tiny example

Exact search is short enough to write by hand. With normalised vectors, cosine similarity is just a dot product:

search.pypython 
import numpy as np def top_k(query, vectors, k=3):    """Indices of the k stored vectors closest to the query."""    q = query / np.linalg.norm(query)    v = vectors / np.linalg.norm(vectors, axis=1, keepdims=True)    scores = v @ q                # cosine similarity    return np.argsort(-scores)[:k]

For a few thousand documents this runs faster than the network call that fetched the query embedding.

04When Postgres is enough

The pgvector extension adds a vector column type, distance operators and HNSW or IVFFlat indexes to Postgres. If your data already lives there, keeping the vectors next to the rows they describe saves you a second system, a sync job and a whole class of consistency bugs.

A dedicated vector database starts to earn its place when the collection is large, the query load is heavy, or you need features like filtered search at scale that you would otherwise build yourself.

05Takeaways

  1. Start with exact search. It is correct by definition and often fast enough.
  2. Reach for an approximate index when latency, not correctness, is the problem.
  3. Keep vectors where your data already lives until that stops working.
